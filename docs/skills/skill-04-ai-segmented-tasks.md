> **适用场景**：用 Codex/Claude/GPT 开发复杂项目时，降低幻觉、避免改崩。

## 标准任务模板

```markdown
# 任务：[具体功能名]

## 范围
只修改 [文件/组件]，不动 [其他模块]。

## 当前问题
[截图/描述]

## 修复要求
### 1. [子任务1]
- 具体代码要求
- CSS/样式规范

### 2. [子任务2]
...

## 验收标准
- [ ] 标准1（可验证）
- [ ] 标准2（可验证）

## 输出
只输出 [文件] 的修改代码，不要其他文件。
```

## 关键原则（4条铁律）

| 原则 | 说明 |
|------|------|
| **一次只改一个组件** | 不给 Codex 多个模块同时修改的任务 |
| **必须有验收标准** | 每条标准必须是可验证的 checkbox |
| **明确"不要动"的范围** | 明确告诉 Codex 哪些文件/逻辑禁止修改 |
| **只输出修改片段** | 要求 Codex 输出"差异代码"，不是完整文件重写 |

## 进阶技巧

### 1. 分阶段交付
```
阶段1：只改数据层
阶段2：只改 API 层  
阶段3：只改前端展示
```
每个阶段验证通过后再给下一个。

### 2. 兜底要求
每次任务结尾必须加：
```markdown
## 注意
- 不要修改路由配置
- 不要修改状态管理逻辑
- 如果报错，先检查 [具体检查项]
```

### 3. 回滚准备
每个阶段改完后立即 commit：
```bash
git add .
git commit -m "feat: [阶段描述]"
```

## 反模式（避免）

- ❌ "帮我优化整个项目" → 范围太大，Codex 会乱改
- ❌ "修复所有 bug" → 没有具体验收标准
- ❌ "重写这个组件" → 容易丢失原有功能
- ❌ 同时给多个不相关的任务 → Codex 会遗漏

## 收益

- 幻觉率降低 80%
- 功能丢失风险趋近于 0
- 每阶段 5-10 分钟可验证
- 出问题可随时回滚到上一阶段
